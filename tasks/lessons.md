# Lessons

## 2026-11-04: dashboard readability feedback
- **No unexplained ratio metrics.** "Drones per armored vehicle destroyed" confused the reader. Show change against a plain baseline instead ("×10 compared with spring 2022") and say what the baseline is in the same sentence.
- **Every mark says what it is.** In the adaptation chart, dots without per-tactic labels left the reader unable to tell what spread or what was countered. Label each item directly with its name and the result ("Fiber-optic FPV: spread in 4 months").
- **Show states over time as bars, not scattered dots.** For lifecycle data, draw one row per tactic with colored segments for each stage ("scaling from May 2025 to now"). Scattered dots made readers decode the phase colors and the time gaps themselves.
- **Before publishing a chart, ask: can someone who has never seen the data say what it shows in one sentence?** If not, simplify it or relabel it.
- **Edit code by anchored definitions, never by bare substrings.** `dash.draw('timeline'` matched a call inside a click handler as well as the definition. Anchor on the line start plus the full signature, check that the count is exactly 1, and syntax-check after every scripted edit.
- **Test unattended jobs in a fresh container before relying on them.** The first scheduled run failed because a top-level `pypdf` import pulled in a broken system `cryptography`. Heavy or optional dependencies are imported only where they're used, and any new scheduled job gets a manual test run immediately.
- **Text that describes data should be generated from the data.** Fixed prose with live numbers goes stale. When the page writes its own summary, pick sentence variants by thresholds and quote the latest source report.
- **Keep separate questions on separate scales.** "How widely is it used?" (an ordered stage) and "has the other side answered it?" (yes/no) were mixed into one phase scale, which made "countered, then dominant" look like nonsense. Before defining categories, check that they are one ordered dimension, and enforce the order in the build.
- **Every highlight color needs a legend, and one color means one thing.** Blue in the per-day charts meant both "peak" and "latest", with no legend, and "faded blue" was a third meaning. Now there is one color per meaning, labels name what they mark ("Latest 3.5", "Peak 17.1"), and a legend sits under the charts. Check every chart for unexplained encodings before publishing.
- **Detrend before correlating time series.** Two series trending in opposite directions correlate strongly by construction. Correlate month-to-month changes, keep the levels only as a labelled contrast, and report n.
- **Event dates must be when things happened.** Retrospective reviews (e.g. RUSI annual papers) carry publication dates, not onset dates. Exclude them from before/after timing tests.
